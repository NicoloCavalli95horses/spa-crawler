# Changelog

## 2026-11-13 14:54 — Parallelize the client-routing analysis phase over a page pool
The end-of-crawl analysis was dominated by the client-routing phase (pushState probe + not-found screenshot per candidate), which serialized on one shared page because each candidate mutates that page's live DOM. On a real busuu crawl this phase ran the analysis to ~6–7 min while the exploration itself took ~1–2.

- **Page pool.** The client-routing phase now runs on a pool of `analysis.clientRoutingConcurrency` pages (default 5), created from the SAME authenticated browser context (shared cookies) with the param-usage init script installed on each; the caller's own page is in the pool, the extras are closed when the run ends. Each probe/screenshot holds a page exclusively (`withPooledPage`), so they run in parallel across pages while staying serial per page — which is all the shared-page serialization ever needed. The retry loop stays on one page, so the rollback-pollution it guards against is always the same candidate's.
- **Forged HTTP requests** keep their own bound (`maxConcurrentRequests`) via a small semaphore, independent of the page pool: they use `page.request.fetch` and need no page DOM.
- **Not-found calibration deduped.** The per-template baseline cache now stores the in-flight promise, so parallel candidates on one template share a single garbage-value render instead of each rendering it.
- Measured on the captured data: pimsleur stays 4/4; busuu analysis **401 s → 78 s (~5×)** with all 19 objective-sibling HTTP IDORs still flagged.

## 2026-11-13 14:40 — Analysis gets its own time budget; faster client-routing probe
Two fixes after a busuu crawl whose analysis ran ~30 min and was then killed by the request-handler timeout.

- **Per-phase time budget.** `requestHandlerTimeoutSecs` was `maxDurationSecs + margin`, but the single request handler runs BOTH exploration and the end-of-crawl analysis, and analysis can be as slow as (here, far slower than) exploration. A crawl whose exploration finished well within budget but whose analysis then ran long was marked *failed* even though the analysis effectively completed. The handler is now sized for both phases (`2 * maxDurationSecs + margin`): `maxDurationSecs` is documented as a per-phase budget — the exploration gets it, then the analysis gets it again. Default raised `1800 → 2700` (45 min per phase).
- **Faster client-routing probe.** `analysis.clientRoutingProbe.maxWaitMs` lowered `4000 → 2500`. The ceiling is only ever paid by a candidate that does NOT react (one that does settles at the floor + idle, ~1.3 s); on a crawl with hundreds of non-reacting client-routing candidates, each probed up to 3×, the 4000 ms ceiling dominated the analysis wall-clock. The not-found screenshot settle (which reuses this value) drops too. Measured on the captured pimsleur data: still flags all 4 IDORs, analysis 13 s → 5 s.

## 2026-11-13 14:09 — Client-routing: client digestion is the primary signal, network is a filter not a veto
A query param (or path segment) can be honoured entirely client-side, with no network traffic at all — the SPA reads the mutated value and renders a different resource. The previous logic over-weighted the network: a `4xx` on any request carrying the candidate value vetoed the finding, and a query candidate was additionally required to have been read through the hooked `URLSearchParams.get`. Pimsleur (lessons routed purely client-side by `?id`) hit exactly this: 3 of 4 real IDORs were dropped. The decision is rebalanced around what this fallback is actually for — confirming the app consumed the mutated value.

- **Primary signal = client digestion.** A candidate is accepted when the SPA rendered the candidate's OWN route and stayed on it (`hasMutatedDom && stayedOnRoute`), unless that render is the app's generic not-found page (the visual baseline guard). `AnalysisPipeline.clientSideConfirmed` now makes this decision for all three client-routing sites.
- **Network demoted to a filter.** A backend `2xx` for the candidate's own value, or a provable param read (`appReadParam`, query only), is corroboration strong enough to accept directly (skip the not-found screenshot). Their absence no longer rejects, and a `4xx` no longer vetoes on its own: a route that renders a real, distinct page is a client-side finding regardless of what some request returned. The hard `URLSearchParams.get` requirement is gone — an app that parses the query string another way is no longer penalised.
- **Boundary-aware network scoping** (`urlCarriesValue`, [src/analysis/clientRouting.ts](src/analysis/clientRouting.ts)). A probe response counts for a candidate only when the value is a WHOLE path segment or WHOLE query-param value, not an arbitrary substring. Fixes a spurious "confirm" where candidate `298` matched the customer id `6140298` that rides along in every authenticated API call.
- `ClientRoutingResult` exposes the raw signals (`appReadParam`, `stayedOnRoute`) the pipeline now weighs; `isUsingNewParams` is kept for reproduction scripts and the flakiness diagnostic. The retry loop ends on client digestion or a 2xx. New unit tests for `urlCarriesValue`.

## 2026-11-13 13:31 — Client-routing probe: network-truth confirm + adaptive DOM-settle window
Two changes make the client-side-routing probe miss fewer legitimate findings. Its DOM-mutation signal, whose timing follows a network-gated render, was the main source of flakiness — an earlier pimsleur run flagged 1 of 4 real IDORs for this reason.

- **A network `2xx` is a positive oracle, not just a veto.** A same-session response carrying the candidate value that the backend answers `2xx` while the probe renders the route is timing-robust evidence the app fetched and served the candidate resource — independent of whether the `MutationObserver` happened to catch the render. A candidate is now accepted on EITHER the DOM signal (`isUsingNewParams`) OR a network confirm; when the network confirms, the not-found screenshot guard is skipped (a `2xx` is not a not-found page). The retry loop also stops as soon as either signal is decisive, so a network-confirmed candidate no longer burns its remaining attempts.
- **Adaptive DOM-settle window** (`waitDomIdle`, [src/analysis/clientRouting.ts](src/analysis/clientRouting.ts)). The old window had a single bound acting as both floor and ceiling: it gave up at `minWaitMs` reporting "no reaction", so a render that only starts mutating after that bound (a slow, network-gated one) was missed, and a page that never went quiet could keep the probe waiting forever. It now has three bounds — floor (`minWaitMs`), DOM-quiet settle (`idleMs`), ceiling (`maxWaitMs`): nothing is reported settled until something actually mutates, so a late first render is still caught up to the ceiling, and the ceiling guarantees termination. Defaults retuned `3000/300` → `1000/300/4000` (lower floor so a quick reaction resolves sooner; a route that never reacts rides to the ceiling).
- New config bound `analysis.clientRoutingProbe.maxWaitMs`, threaded through `buildExplorer`, `scripts/runAnalysisFromDb.ts` and generated reproduction scripts. The not-found screenshot baseline settles on the ceiling (a visual baseline wants the fully-rendered route, not the floor).
- Verified on the captured pimsleur data (non-destructively, on a DB copy with its findings pre-cleared): the new code flags all 4 of 4 known IDORs (`294/295/297/298`), none rejected.

## 2026-11-13 11:39 — runAnalysisFromDb: `LOG_LEVEL=debug` to see per-candidate decisions
`scripts/runAnalysisFromDb.ts` now honors `LOG_LEVEL` (`debug` turns on crawlee's DEBUG level, otherwise INFO), so a re-run on already-captured data logs why each candidate was accepted or rejected — the per-candidate "rejected (...)" / "potential access control issue" lines. Useful for diagnosing whether a filter (network truth, not-found screenshot, authz relevance, client-routing flakiness) is responsible for an unexpected count.

## 2026-11-13 11:23 — Client-routing false-positive guards: network truth + not-found screenshot baseline
A client-routing candidate is now flagged only when its route resolves to a real, distinct resource, not to an error page or the app's own not-found page. Two independent guards decide this, both scoped to client-side findings (an HTTP/JSON finding already has the server-response oracle):

- **Network truth.** While the probe renders the candidate route, the status of the request the app itself fires for the candidate value is recorded (`page.on('response')`, scoped by the value so the probe's own rollback fetch and analytics never count). Any `4xx` — the backend denied the swap or the resource does not exist — rejects the candidate; a `2xx` confirms it. Carried on `ClientRoutingResult.probeRequests` from `checkClientSideRouting`/`checkClientSideRoutingForPath`.
- **Not-found screenshot baseline** ([src/analysis/routeScreenshot.ts](src/analysis/routeScreenshot.ts)). When no backend call carries the value (a purely client-routed page), a screenshot of the candidate's render is compared (pngjs + pixelmatch) against the app's not-found page — calibrated once per route template by rendering a garbage id in the same slot. A render within `analysis.notFoundScreenshotMaxDiff` (default 0.02) of that baseline is rejected.
- New config knob `analysis.notFoundScreenshotMaxDiff`; `checkClientSideRoutingForPath` takes an optional `candidateValue` for the network scope.
- Measured on the captured busuu data (non-destructively, on a DB copy): 114 → 113 findings. The guards are correct but had little to remove here — busuu's client-routing findings are dominated by objective siblings whose backend genuinely answers `2xx` (kept) and by swaps between two valid navigation sections (`dashboard` ↔ `review`, which render real, different pages, so neither guard applies). Exactly one candidate, whose component fetch returned `4xx`, was removed. Datasets with client-side `404` renders benefit more; the navigation-word-swap false positives remain a separate, open problem.

## 2026-11-13 10:33 — Client-routing probe no longer crashes the whole analysis run
A client-routing probe (`checkClientSideRouting`/`checkClientSideRoutingForPath`) fires a synthetic `pushState` + `popstate`; for some candidate paths this makes the app's own router perform a REAL navigation, which destroys the page's execution context mid-`page.evaluate` (`Execution context was destroyed, most likely because of a navigation`). That rejection was unhandled: it propagated through `runWithConcurrency` and aborted the entire `runForSite` partway through the client-routing phase, losing `analysis_stats` and every not-yet-dispatched candidate (observed on busuu after all 51 HTTP findings had been persisted but before the client-routing ones).

- Both probes now run their script through a small `evaluateProbe` wrapper that catches any `page.evaluate` failure and returns a benign "the app did not react" result (`isUsingNewParams: false`). A destroyed context is never evidence of an authorization issue (the candidate was never confirmed to render), so dropping it is both safe and correct; the caller's queue already re-navigates to the page URL before the next probe.
- Defense in depth: `AnalysisPipeline` now wraps each dispatched candidate task so a single task throwing is logged and skipped instead of rejecting the whole bounded-concurrency pool — one bad candidate can no longer abort the run and discard the stats + remaining findings.

## 2026-11-13 10:27 — Candidate generation: drop generic-keyword segments + cache parsed React graphs
The analysis pipeline's pre-dispatch phase (turning captured URLs into IDOR candidates) took ~20 minutes of pure CPU on busuu before a single request was forged. Two compounding causes, both fixed; on the same data the phase now runs in ~2s instead of >115s (measured offline over 10,752 URLs).

- **Generic-keyword segments skipped.** `extractSegments` proposes every URL path segment as a "swap this value" candidate, filtered only by "does the value appear in the preindex". Generic segments that happen to also be React values — DOM tags / aria roles / category words like `svg` (21k nodes), `grammar` (3.7k), `vocabulary` (6.8k) — matched thousands of preindexed nodes each, and the fan-out (every match × its component siblings, across every URL sharing the word) exploded combinatorially and produced thousands of junk candidates. `AnalysisPipeline.findUrlCandidates` now skips a segment whose value appears in more than `config.analysis.maxSegmentMatches` preindexed nodes (default 300), via the new `PreindexedValueStore.countByValue` (an indexed `COUNT`, never materializing the rows). Real identifiers are far below the cap (busuu objective/exercise/activity ids appear 20–110 times), so the surviving candidates are unchanged — e.g. `objective_e43c5b7a` still yields exactly its 19 sibling candidates.
- **Parsed React graphs cached per run.** `findUrlCandidates` looked a state's graph up once per preindex match (tens of thousands of times) but there are only a couple hundred distinct graphs; it was re-running `JSON.parse` on the same ~150 KB strings repeatedly. `AnalysisPipeline` now memoizes `getById` for the duration of a `runForSite` (cleared at its start, so it never grows across sites or goes stale).
- New config knob `analysis.maxSegmentMatches` (threaded through `buildExplorer` and `scripts/runAnalysisFromDb.ts`). Note: this only addresses the pre-dispatch phase; the serialized client-routing probes remain a separate cost.

## 2026-11-13 09:06 — Tolerant restore: attempt budget for (state, element)
Restoring a state no longer abandons an element (or the branch below it) on the first failure. In SPA environments, an intermittent interstitial at page load (cookie banner, “welcome back” bottom sheet) may cover the target on one page load and disappear on the next: previously, this was enough to prune entire exploration branches, because the `(state, element)` pair was marked as explored *before* the attempt, and a single miss was final.

- `StateStore` transitions from destructive marking (`isExplored`/`markExplored`) to a `untried → inprogress → done` lifecycle using `claim()`/`release()`. `claim()` remains the synchronous and exclusive gate that prevents two tabs from clicking the same element; a `release(‘miss’)` puts the pair back in the queue for a new attempt on a future landing, as long as there is budget, then closes it (guaranteed termination). An exception during the click immediately closes the pair (actual error, not volatility): it is not retried.
- `DfsExplorer.step` now distinguishes between “element found and clicked” and “missed this time”; `claimable()` scans the frontier and retrieves a state only when *all* of its elements are `done`, skipping (without removing) states with only `inprogress` elements.
- New configuration parameter `restoreAttempts` (default 4): the number of times a pair is retried across multiple landings before being deemed unreachable.
- The set of clickable elements remains that of the original snapshot for each state: *new* clickable elements that appear only in variants (e.g., buttons in the intermittent modal) are treated as volatile and ignored; those already captured are simply re-located with tolerance.
